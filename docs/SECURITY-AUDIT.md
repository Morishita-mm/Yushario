# セキュリティ監査と修正

## 対象と前提

初回監査は `362aeea` を対象に、ローカルHTTP／WS入口、フックとエージェントの認可、PTY起動、Git／worktree操作、差分・静的ファイルの境界、プレビュー、表示・保存処理、依存関係を確認した。悪意ある同一OS利用者とのプロセス・ファイル隔離は対象外。

修正は最新mainの `2182567` を基点とする。この間に追加されたモバイル窓口を含めた全体の再監査ではない。ソースレビュー、coreの再現実験、依存監査に加え、今回の変更は一時データフォルダで起動した本番ビルドへの実HTTP／WSでも確認した。ブラウザ上の攻撃再現や侵入試験全般は行っておらず、安全性を保証するものではない。

## 1. 中：未認証イベントによる表示状態の無制限増加 → 修正

`src/server/relay-hooks.ts` は未認証イベントを `external:` 名前空間で表示用に受け付けていた。履歴は2000件に制限していても、接続中の画面の `Room.agents` はSessionEnd以外で減らず、生存中のhelpersにも件数上限がなかった。

初回のcore再現結果：異なる5000 IDでhistory=2000、Room.agents=5000。同じ勇者への5000個のSubagentStartでhelpers=5000。

同一マシンの別OS利用者など、loopbackへOriginなしのHTTPを送れる送り元が、トークンなしでメモリ・CPU消費を増やせた。外部WebページからはHost検証とOrigin拒否があるため、そのまま攻撃できるものではない。台帳改ざん・PTY操作への昇格は確認していない。

### 修正内容

- `src/core/hook-trust.ts`：未認証イベントの受付判定を純粋関数化。全体で1秒30件、起動中に受け付ける異なるIDは32件まで。送り元IPや自己申告IDごとに頻度枠を分けない。
- `src/server/relay.ts`：履歴追加・配信より前に上記判定を適用。時刻はサーバーの受信時刻を使い、本文の `ts` で制限を回避できない。認証済み端末のイベントはこの枠を使わない。
- `src/server/relay-hooks.ts`：超過した `/event` は429。未認証の許可フックの表示分も同じ枠を通し、超過時も従来どおり200の `{}` で端末判断へ戻す。
- `src/core/room.ts`：生存中の仲間は勇者ごと64件まで。上限時も既存の仲間の更新・終了を処理し、空いた枠には新しい仲間を迎えられる。

ID枠はSessionEndで解放せず、再起動まで保持する。終了で枠を再利用すると、画面の名前・退場履歴へ異なるIDを際限なく追加できるため。上限後も既知の外部IDは再び受け付ける。新しい外部IDを表示するにはサーバーを再起動する。認証済み端末はこの制約を受けない。

これは表示イベントの受付・保持量の制限であり、接続数や受信本文のパースを含むHTTP負荷全般を防ぐ対策ではない。

## 2. 中：Vitest 4.1.11の既知脆弱性 → 既存の更新を確認

初回の `npm audit` は `vitest` と推移依存 `@vitest/mocker` にmoderateを報告した。関連アドバイザリ：

- [GHSA-qxg6-89mg-rqv8](https://github.com/advisories/GHSA-qxg6-89mg-rqv8)：未認証のmanual mock登録を通じたコード注入。
- [GHSA-xp26-3454-mjgp](https://github.com/advisories/GHSA-xp26-3454-mjgp)：Windowsのバックスラッシュによるredirect allowlist迂回。

該当するVitestサーバー／mocker機能が攻撃可能な状態で動く開発環境に関係する。本番サーバーからの悪用やWindows上の攻撃再現は行っていない。

修正基点のmainには `bb5aa9e` でVitest 4.1.12と更新済みロックファイルがすでに入っていた。今回のPRでは重複更新せず、`npm ci` 後に `vitest`／`@vitest/mocker` がともに4.1.12であることと、全依存の `npm audit` が0件であることを確認した。新しい依存の追加はない。

## 検証結果

- `npm run typecheck`：成功。
- `npm test`：78ファイル、889テスト成功（追加5テスト）。
- `npm run build`：web／serverとも成功。
- `npm audit --json`：全severityで0件。
- `src/core/external-events.test.ts`：5000 IDの入力、窓をまたいだID上限、頻度制限の境界・時計の巻き戻り・状態の非破壊、認証済み勇者の保持、認証済み／未認証それぞれの5000仲間・上限中の更新と終了を検査。
- 実HTTP／WS：1秒30件を超える `/event` の429、32 IDを超える新規IDの429、既知IDの再受付、本文の未来時刻で回避できないこと、拒否イベントが配信されないこと、許可フックの200 `{}`、外部Originの403を確認。一時データフォルダは終了後に削除。

## 今回変更していない防御強化候補

- プレビューは `postMessage` 通知のためopenerを保持する。別originのプレビューが親DOMやトークンを読めるわけではないが、親画面のナビゲーションを試みる余地はある（ブラウザの制限あり）。`noopener` をそのまま加えると既存通知が壊れるため、通知方式の変更はこのPRには含めない。
- WS送信に `bufferedAmount` 上限がない。遅い認証済みクライアントへの送信待ち対策は別途検討する。`maxPayload` は受信側だけの上限。
