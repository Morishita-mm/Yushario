# Mobile companion（設計・計画）

Yushario の勇者の様子をスマホで知り、許可要求に答えるための小さな別アプリ。Yushario をスマホへ移植するものではない。
この文書は着手前の設計で、実装・検証の進み具合に合わせて更新する。決定済みの事項と未決の事項を分けて書く。

## 前提（決定済み）

- 通知は必須。iOS と Android の両方を作る。開発者自身は Android、友人は iPhone を使う。
- 配る相手は開発者と友人。各自が自分の Mac で Yushario を動かし、自分のスマホとだけ組む。共有のサーバーは運営しない。
- アプリは Expo / React Native で作り、別リポジトリに置く。Yushario 本体には「モバイル窓口」だけを足す。
- 通知は Expo の通知サービス（Expo Push Service）で APNs・FCM へ届ける。通知に作業の中身は載せない。
- Apple Developer Program は完成の目処が立ってから登録する。それまでは Android 実機と iOS シミュレーターで開発する。
- セキュリティの検証は内部で行い、コミットに結び付いた証跡を残す。第三者の検証は今の段階では入れない。
- 参考にする設計：Orca のモバイル連携（使い捨てのペアリングコード、経路に依存しないアプリ間の暗号化、LAN／Tailscale の切り替え）。

## 機能の範囲

| 区分 | 機能 |
|---|---|
| 最初の版 | 通知を受ける（許可待ち・報告・失敗）／許可要求を承認・拒否する／勇者の一覧と状態を見る／報告の要約を読む |
| 後で判断 | 勇者に依頼を送る（遠隔からのコード実行と同じ重さのため、最初の版では作らない） |
| 作らない | ターミナル、ワークツリー・Git の操作、差分の全文、町の描画、勇者の出陣・終了 |

## 構成

```text
[スマホのアプリ] ══ アプリ間の暗号化 + 端末の署名 ══ [Mac: モバイル窓口] ── プロセス内 ──▶ [Yushario server]
   経路は LAN か Tailscale（どちらも同じ扱いで、経路の暗号化には頼らない）            │
        ▲                                                                      │
        └── APNs / FCM ◀── Expo Push Service ◀── 中身のない通知 ─────────────────┘
```

- **モバイル窓口**は、Yushario の起動時に `--mobile` を付けた時だけ動く。既存の server とは別のポートで待ち受ける。
  - 待ち受けるアドレスは利用者が明示する（Tailscale の IP や LAN の IP）。既定では動かない。`0.0.0.0` を選んだ場合は警告する。
  - ブラウザ用の API・`/pty`・`/ws` とは経路を共有しない。窓口の処理は下の許可リストの操作だけを、server の既存処理（許可の判断など）へ渡す。
- **アプリ**は、Mac を複数登録できる（自宅の Mac を2台など）。登録した Mac ごとに経路のアドレスを持ち、ペアリングし直さずに変更できる。

## プロトコル

### 鍵

| 持ち主 | 鍵 | 置き場所 |
|---|---|---|
| Mac（窓口） | 暗号用 X25519 と署名用 Ed25519。窓口の初回起動時に作る | `AGENT_CHARACTER_HOME` の窓口用ファイル（権限 0600）。利用者が作り直せる |
| スマホ | 暗号用 X25519 と署名用 Ed25519。Mac ごとに作る | OS の安全な保管庫（iOS Keychain の「この端末のみ」、Android Keystore で暗号化）。バックアップに含めない |

- 暗号の部品：X25519 で鍵を共有し、HKDF-SHA256 で鍵を導き、ChaCha20-Poly1305 で暗号化する。署名は Ed25519。
- Mac 側は Node 標準の `crypto` だけで作る（依存を足さない）。アプリ側は監査済みの `@noble/curves`・`@noble/ciphers`・`@noble/hashes` を使う。
- 両方のリポジトリで同じテスト用データ（決まった入力と期待する出力の組）を共有し、両方で通ることを確かめる。

### ペアリング

1. 利用者が Mac の画面で「スマホを登録」を押す。Mac は使い捨てのコード（128bit の乱数）を作り、QR コードに「窓口のアドレス・Mac の公開鍵・コード・期限」を入れて表示する。期限は5分で、使えるのは1回だけ。
2. スマホが QR コードを読み、端末の鍵を作る。Mac の公開鍵宛てに暗号化したペアリング要求（端末の公開鍵・端末名・通知用 ID・コード）を送る。
3. Mac は、両方の公開鍵から作った6桁の確認番号と端末名を画面に出す。利用者がスマホにも同じ番号が出ているのを確かめ、Mac 側で承認した時だけ登録する。
4. 登録できる端末は Mac ごとに最大5台。コードの失敗は1つのコードにつき3回までで、超えたらコードを失効させる。

QR コードで Mac の公開鍵を直接受け取るので、経路の途中で鍵をすり替えることはできない。

### 要求と応答

- 要求はすべて「端末 ID・連番・時刻・本文」を端末の鍵で署名し、共有した鍵で暗号化する。応答も暗号化する。
- Mac は、署名・登録済みの端末か・連番が前回より大きいか・時刻が前後60秒以内か、を検査し、どれかが合わなければ理由を明かさずに断る。
- プロトコルの版を要求に含め、合わない時は接続を断ってアプリの更新を促す。

### 許可リスト（窓口が受け付ける操作のすべて）

| 操作 | 内容 |
|---|---|
| `pair` | ペアリング要求。ペアリング中のコードがある時だけ受け付ける |
| `status` | 勇者の一覧と状態（名前・町の表示名・状態・許可待ちの有無） |
| `permissions` | 待っている許可要求の一覧（コマンドやパスを含む。既存の120秒の期限と2000文字の上限に従う） |
| `decide` | 許可要求1件への承認・拒否 |
| `reports` | 報告の要約（題・成否・時刻と、本文の先頭） |
| `push-token` | 通知用 ID の登録・更新 |
| `unpair` | 自分の端末の登録を消す |

### 許可の判断

- アプリは承認・拒否の前に、必ず生体認証（または端末のロック解除）を求める。
- `decide` には、許可要求の ID と、画面に表示した内容のハッシュを含める。Mac はハッシュが今の内容と一致し、期限内で、まだ答えていない時だけ受け付ける。
- 判断は既存の `permission-decision` と同じ処理へ渡す。自動承認はしない。ブラウザと同時に答えた場合は、先に届いた方を採る。
- 誰がいつ判断したか（端末 ID・許可 ID・結果・時刻）を窓口の記録に残す。コマンドの本文は残さない。

### 通知

- 送る契機は、許可待ち・報告・失敗。題と本文は固定の文言にする（例：「Yushario」「確認が必要です」）。勇者名・コマンド・パスは載せない。
- アプリは通知を開いた後、窓口へ `permissions` や `reports` を取りに行く。経路に届かない時は「Mac に接続できません」と表示する。
- 通知用 ID は窓口のファイルに保存し、端末の登録を消した時に消す。この ID が漏れても、できるのは偽の「確認が必要です」を送ることだけで、承認はできない。

### 端末の取り消し

- Mac の画面に登録済みの端末を一覧し、個別に取り消せる。取り消した端末の要求はすぐに断る。
- アプリからは自分の登録だけを消せる。

## 脅威モデル

| ID | 脅威 | 対策 | 確かめる検査 |
|---|---|---|---|
| T1 | 同じネットワークの他人が窓口に要求を送る | 端末の署名、未登録の端末を拒否 | SEC-01 |
| T2 | QR コードを盗み見て先にペアリングする | 5分・1回限りのコード、Mac 側での確認番号の承認 | SEC-02, SEC-03 |
| T3 | ペアリング中に経路で鍵をすり替える | Mac の公開鍵を QR で受け取る | SEC-04 |
| T4 | 承認の要求を再送する | 連番・時刻・許可 ID の1回限りの受け付け | SEC-05 |
| T5 | 経路で要求を書き換える | AEAD による暗号化、改ざんを拒否 | SEC-06 |
| T6 | Apple・Google・Expo に作業の中身が渡る | 通知は固定の文言だけ | SEC-07 |
| T7 | 通知用 ID の漏れによる偽の通知 | 通知では操作できない。端末の登録を消すと ID も消える | SEC-08 |
| T8 | スマホの紛失・盗難 | 承認ごとの生体認証、Mac からの取り消し、鍵を安全な保管庫に置く | SEC-09, SEC-10 |
| T9 | 窓口をインターネットへ公開してしまう | 既定で停止、アドレスの明示、`0.0.0.0` の警告 | SEC-11 |
| T10 | 窓口から `/pty` などの操作に届く | 別のポート、許可リスト以外の操作を拒否 | SEC-12 |
| T11 | ペアリングコードの総当たり・大量の要求 | 128bit のコード、3回で失効、本文の上限、要求数の制限 | SEC-13 |
| T12 | 表示と違う内容を承認させられる | 承認に表示内容のハッシュを結び付ける | SEC-14 |
| T13 | 誰が承認したか分からない | 判断の記録 | SEC-15 |
| T14 | アプリの依存パッケージの汚染 | 依存の最小化、lockfile の固定、脆弱性の検査 | SEC-16 |
| T15 | 鍵がバックアップから漏れる | 「この端末のみ」の保管、バックアップから除外 | SEC-17 |

## 検証と証跡

- 証跡は `docs/security/`（窓口）とアプリのリポジトリの同じ場所に置く。
  - `threat-model.md`：上の表を正として育てる。
  - `checklist.md`：アプリは OWASP MASVS、窓口は OWASP ASVS レベル2の該当項目ごとに、対応と証拠へのリンクを書く。
  - `runs/<日付>-<コミット>.md`：検証した日付・対象のコミット・手順・結果・使った道具の版。
- 自動の検査（CI で毎回実行）
  - SEC-xx のうち自動化できるもの。窓口の検査は、実際の HTTP で窓口を立てて要求を送る形にする。
  - 共有のテスト用データによる暗号の検査（Mac 側とアプリ側の両方）。
  - CodeQL、依存の脆弱性検査（`npm audit` と OSV-Scanner）、秘密情報の検査（gitleaks）。
- 手動の検査（リリースごと）
  - 実機での操作の確認（生体認証・取り消し・紛失を想定した手順）。
  - アプリのビルドを MobSF で検査する。
- リリースの条件：そのコミットの `runs/` がそろい、未対応の SEC 項目がないこと。

## 進める順番

1. この文書の合意と、`ARCHITECTURE.md`・`AGENTS.md` の更新（下の「本体側で変えること」）。
2. 暗号とプロトコルの仕様書・テスト用データ（Yushario の `src/core` に純粋関数として置く）。
3. モバイル窓口（Yushario 本体、ブランチ + PR）と SEC 検査。
4. アプリのリポジトリを作り、Android でペアリング・状態・許可・報告・通知を作る。
5. iOS シミュレーターで確認する（APNs の実配送は Apple Developer の登録後）。
6. 検証の実施と証跡のまとめ。
7. Apple Developer に登録し、TestFlight で友人に配る。

## 本体側で変えること

- `ARCHITECTURE.md` の「PoC でやらないこと」から、スマホ対応とインターネット経由の利用（窓口の範囲に限る）を外し、窓口の境界と許可リストを「インタフェース」に書く。
- `AGENTS.md` のテストの規則に、窓口のセキュリティ検査を例外として加える（実際の HTTP で窓口を立てる形）。
- 窓口が Yushario に足す依存はなし（Node 標準の `crypto` と既存の `http`）。

## 未決の事項

- 窓口の待ち受けを `--mobile` 起動時だけにするか、設定画面から切り替えられるようにするか。
- 報告の要約に本文の先頭をどれだけ含めるか（スマホの画面に作業の中身が出る量）。
- アプリの名前とアイコン。
- Android の配布方法（Google Play の開発者登録は25ドルの一回払い。登録しない場合は APK を直接渡す）。
