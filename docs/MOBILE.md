# Mobile companion（設計・計画）

Yushario の勇者の様子をスマホで知り、許可要求に答えるための小さな別アプリ。Yushario をスマホへ移植するものではない。
Mac の窓口・登録画面・自動の SEC 検査を実装した。別アプリと実機の検証・配布は別の段階で、[security/checklist.md](security/checklist.md) の未実施項目がリリース条件として残る。決定済みの事項と未決の事項を分けて書く。

## 前提（決定済み）

- 通知は必須。iOS と Android の両方を作る。開発者自身は Android、友人は iPhone を使う。
- 配る相手は開発者と友人。各自が自分の Mac で Yushario を動かし、自分のスマホとだけ組む。共有のサーバーは運営しない。
- アプリは Expo / React Native で作り、別リポジトリに置く。Yushario 本体には「モバイル窓口」だけを足す。
- 通知は Expo の通知サービス（Expo Push Service）で APNs・FCM へ届ける。通知に作業の中身は載せない。
- Apple Developer Program は完成の目処が立ってから登録する。それまでは Android 実機と iOS シミュレーターで開発する。
- セキュリティの検証は内部で行い、コミットに結び付いた証跡を残す。第三者の検証は今の段階では入れない。
- 参考にする設計：Orca のモバイル連携（使い捨てのペアリングコード、経路に依存しないアプリ間の暗号化、LAN／Tailscale の切り替え）。

## 機能の範囲

| 区分 | 機能 |
|---|---|
| 最初の版 | 通知を受ける（許可待ち・報告・失敗）／許可要求を承認・拒否する／勇者の一覧と状態を見る／町を選んでクエストの札を発行する／クエスト一覧と報告の本文を読む |
| A2（勇者を動かすものは Mac で端末ごとに許可した時だけ） | 札から勇者に依頼を送る／Claude・Codex を出陣させる／パーティーを組んで出発させる（遠隔実行。下記「勇者を動かす操作」） |
| A3（町の所属・姿） | 町ごとにまとめる不透明 ID と、同梱の小さい絵を選ぶ5種の theme を返す（画像の配信・画面は別） |
| 作らない | ターミナル、ワークツリー・Git の操作、差分の全文、町の全景の描画、勇者の終了・呼び戻し・引き継ぎ、クエストの状態変更・採用・削除、Pi の新規出陣 |

## 構成

```text
[スマホのアプリ] ══ アプリ間の暗号化 + 端末の署名 ══ [Mac: モバイル窓口] ── プロセス内 ──▶ [Yushario server]
   経路は LAN か Tailscale（どちらも同じ扱いで、経路の暗号化には頼らない）            │
        ▲                                                                      │
        └── APNs / FCM ◀── Expo Push Service ◀── 中身のない通知 ─────────────────┘
```

- **モバイル窓口**は、Yushario の起動時に `--mobile <host:port>` を付けた時だけ動く。既存の server とは別のポートで待ち受ける。
  - 待ち受けるアドレスは利用者が明示する（Tailscale の IP や LAN の IP）。既定では動かない。`0.0.0.0` を選んだ場合は警告する。
  - ブラウザ用の API・`/pty`・`/ws` とは経路を共有しない。窓口の処理は下の許可リストの操作だけを、server の既存処理（許可の判断など）へ渡す。
- **アプリ**は、Mac を複数登録できる（自宅の Mac を2台など）。登録した Mac ごとに経路のアドレスを持ち、ペアリングし直さずに変更できる。

## Mac と Android エミュレーターでためす

```sh
npm run dev -- --mobile 127.0.0.1:8791 --no-open
# または npm run build の後:
node scripts/yushario.mjs --mobile 127.0.0.1:8791 --no-open
```

Mac の画面で「スマホ」→「スマホを登録」を開く。Android エミュレーターへ渡す接続先だけ `http://10.0.2.2:8791` に直し、QR またはコピー文字列をアプリへ渡す。待受は `127.0.0.1` のままでよい。6桁を比較して Mac で承認する。実機では明示した LAN／Tailscale アドレスを使う。flag なしでは listener を作らず「スマホ」も隠す。

### 窓口の再起動とロックの復旧

- `AGENT_CHARACTER_HOME/mobile/gateway.lock` は、同じ鍵・連番を2つの窓口が使わないための排他ファイル。原子的な新規作成で取得し、正常終了で自分の lock を消す。
- 異常終了で lock が残った場合も**自動では削除しない**。古い PID だと判断してから削除する方式は、同時起動した別プロセスの新しい lock を消す競合になるため、起動を拒否する。
- 起動エラーには lock の正確な絶対パスと、記録が読めれば PID・開始時刻（UTC）を表示する。新しい lock はこの2値の JSON、旧版の PID だけの lock も診断に使う。PID の再利用もあるので、番号だけで停止済みと決めない。
- **同じ AGENT_CHARACTER_HOME を使う Yushario と自動再起動元がすべて停止していることを確認してから**、エラー末尾に表示する `rm -- '…/mobile/gateway.lock'` のコマンドで、その1ファイルだけを消して再起動する。動いている窓口の lock は絶対に消さない。
- `state.json` は鍵・登録・連番の本体なので、復旧のために削除・初期化・古い版へ差し戻してはいけない。lock だけを消す復旧では登録をやり直す必要はない。state の破損は元ファイルを保全して別途調べる。

## プロトコル

通信のバイト列・本文・暗号の入力・共有テスト用データは [MOBILE-PROTOCOL.md](MOBILE-PROTOCOL.md)（v1）が正。

### 鍵

| 持ち主 | 鍵 | 置き場所 |
|---|---|---|
| Mac（窓口） | 暗号用 X25519 と署名用 Ed25519。窓口の初回起動時に作る | `AGENT_CHARACTER_HOME` の窓口用ファイル（権限 0600）。利用者が作り直せる |
| スマホ | 暗号用 X25519 と署名用 Ed25519。Mac ごとに作る | OS の安全な保管庫（iOS Keychain の「この端末のみ」、Android Keystore で暗号化）。バックアップに含めない |

- 暗号の部品：X25519 で鍵を共有し、HKDF-SHA256 で鍵を導き、ChaCha20-Poly1305 で暗号化する。署名は Ed25519。
- Mac 側は Node 標準の `crypto` だけで作る（依存を足さない）。アプリ側は監査済みの `@noble/curves`・`@noble/ciphers`・`@noble/hashes` を使う。
- 両方のリポジトリで同じテスト用データ（決まった入力と期待する出力の組）を共有し、両方で通ることを確かめる。

### ペアリング

1. 利用者が Mac の画面で「スマホを登録」を押す。Mac は使い捨てのコード（128bit の乱数）を作り、QR コードに「窓口のアドレス・Mac の公開鍵・コード・期限」を入れて表示する。期限は5分で、使えるのは1回だけ。
2. スマホが QR コードを読み、端末の鍵を作る。端末の公開鍵を認証付きヘッダーに置き、Mac の公開鍵宛てに暗号化したペアリング要求（端末名・通知用 ID・コード）を送る。
3. Mac は、両側の暗号用・署名用公開鍵とコードから作った6桁の確認番号と端末名を画面に出す。利用者がスマホにも同じ番号が出ているのを確かめ、Mac 側で承認した時だけ登録する。「この端末から依頼・出陣も許可する」は既定オフで、承認時に選んだ値を登録と同時に保存する。承認後は「あとから 下の各スマホの「スマホからの依頼・出陣を許可」で変えられます」と案内し、一覧には登録日時と最後の接続を表示する（名前の変更は扱わない）。
4. 登録できる端末は Mac ごとに最大5台。コードの失敗は1つのコードにつき3回までで、3回目でコードを失効させる。

QR コードで Mac の公開鍵を直接受け取るので、経路の途中で鍵をすり替えることはできない。

### 要求と応答

- 要求はすべて「端末 ID・連番・時刻・本文」を端末の鍵で署名し、共有した鍵で暗号化する。応答も暗号化する。
- Mac は、署名・登録済みの端末か・連番が前回より大きいか・時刻が前後60秒以内か、を検査し、どれかが合わなければ理由を明かさずに断る。
- プロトコルの版を要求に含め、合わない時は接続を断ってアプリの更新を促す。

### 許可リスト（窓口が受け付ける操作のすべて）

| 操作 | 内容 |
|---|---|
| `pair` | ペアリング要求。ペアリング中のコードがある時だけ受け付ける |
| `status` | 勇者の一覧と状態（名前・町の表示名・状態・許可待ちの有無） |
| `permissions` | 待っている許可要求の一覧（コマンド／パス、受信時の担当クエスト、変更の本文。120秒の期限、本文の上限は A4 を参照） |
| `decide` | 許可要求1件への承認・拒否 |
| `towns` | 表示名と窓口内だけで解決するランダム ID（100件ずつ）。内部の町の鍵・パスは返さない |
| `quests` | クエストの題・町の表示名・状態・最終更新（100件ずつ） |
| `quest-create` | 既知の町に題・目的を持つ未着手の札を作る。送信・担当・出陣はしない |
| `quest-options` | 町の勇者（表示名・preset／装備のラベル・状態・permissionGate）、拠点、出陣できる preset と装備の不透明 ID、この端末の作業許可 |
| `quest-draft` | 札の下書き（依頼文・作戦・メンバー・作戦の適合・出発の状態） |
| `quest-prepare` | 札を作り、既存の勇者へ送る／既存の勇者を割り当てる／新しい勇者を出陣させて割り当てる（本文は送らない）／パーティー用にする |
| `quest-form` | パーティーの下書き（依頼文・メンバー・作戦）を保存し、メンバーを割り当てる。送らない（しき役・忙しい勇者・付け替えは送信と同じ許可と枠が必要） |
| `quest-embark` | 札のために新しい勇者を出陣させてメンバーに加える |
| `quest-depart` | 保存したパーティーを出発させる（メンバーごとに1回だけ送る） |
| `reports` | 最近50件の要約とクエストの題、または指定したクエストの報告を時刻昇順に8件ずつ（本文最大8000文字、無ければ null） |
| `push-token` | 通知用 ID の登録・更新 |
| `unpair` | 自分の端末の登録を消す |

### クエストの発行と報告の読み取り

- 作成は既存 `validQuestPatch`・町の登録確認・`QuestLedger.create` を使う。題は空白だけを不可とする200文字、目的は空可の2000文字（UTF-16）。目的はクエストの札として常時保存するが、エージェントへの依頼文として送らない。
- `quest-create` 自体は `say`・担当の割当・出陣・パーティー編集・done/adopt を引数に取らない。作成しても状態は open、担当・拠点・出来事はなく、CLI・PTY・作戦を起動しない（勇者を動かすのは A2 の別操作だけ）。
- **作成ごとの生体認証／ロック解除は追加しない**。札を記録するだけでコード実行・許可・配送に進まないため。登録鍵による認証、Mac からの取り消し、端末ごと直近60秒で5件の作成上限で悪用を制限する。`decide` は従来どおり毎回必須。OS による本人確認の完了を窓口が証明するものではない。
- 要求 ID はアプリが明示送信時に1度だけ作る `時刻.B64(乱数16バイト)`。10分で期限切れ（未来60秒までの時計差を許容）。窓口は ID を作成より前に0600の `mobile/quest-requests.json` へ fsync・rename・ディレクトリ fsync で予約し、同じ ID は本文・端末・連番を変えても拒否する。再起動でも保持し、期限切れ ID は記録を間引いた後も時刻検査で拒否する。予約は最大1000件、作成回数も予約から計算する。
- 連番の永続予約・HTTP 自動再送禁止は不変。応答消失時は一覧を読み直す。同じ ID の新しい連番での再提出も一般拒否になり、作成済みかは断定しない。アプリは失敗時に新しい ID を自動発行しない。予約後の障害では札が作られない場合もある（at-most-once を優先し、再開・自動配送しない）。
- 窓口の `mobile/quest-creations.jsonl` は0600で `{deviceId,questId,time}` だけを作成前に記録する。保存失敗なら作成しない。本文・目的・町のパス・要求本文は残さない。これは発行の予約記録で、直後に停止すると対応する札が存在しない場合がある。
- 町の ID は窓口のメモリ内の対応表だけを使う UUID で、内部の鍵の hash/base64 ではない。再起動で無効になるので町一覧を取得し直す。クエストの町が現在の台帳になければ表示は「町」とし、パスを代用しない。
- 報告は保存済みの本文、無ければ同じ勇者・報告時刻のメモリの最終返答だけを読む。`saveConversation=false` の本文は新たに保存しない。再起動・会話の保持期限後は null。任意の cwd・branch・拠点・ファイル一覧・コマンド出力・許可内容のフィールドや別種の出来事は返さない。題と返答の文章自体は人／CLI が書いた内容であり、機密の自動分類・要約・墨消しは行わない。
- ページの cursor は直前の最後の ID。一覧はスナップショット固定ではないので、作成・更新・削除後や cursor 拒否時は先頭から再取得する。

### 町の所属と姿（A3）

- Hero・Permission・Quest・Report・WorkHero・WorkBase・WorkDraft に必須の `townId:string|null` を追加。Town.id と同じ窓口メモリ内のランダム UUID v4 で、同名の町を混同しない。再起動・削除後は取り直す。未登録・削除済み・所属不明は null、終了済み WorkHero も null。報告は勇者の現在地でなくクエストの町に属する。既存の town 表示名は残す。
- Town に `theme:"village"|"port"|"snow"|"desert"|"volcano"|null` を追加。Mac の町画面と同じ TownRecord.theme だけを使い、未知・未設定なら null。パス・cwd・branch のフィールドや、フォルダ名から推測した値・画像の URL は出さない。アプリは同梱の絵を選ぶ。
- 件数は追加しない。アプリが取得した行を townId でまとめて数えられるため。status 最大100／許可16／最近報告50とページの上限を守り、「表示中」の件数にする。クエスト全件の数は全ページを読み終えてから求める（進行中は active/waiting/review）。別要求間の snapshot 保証はない。
- 未配布の開発アプリを同時更新する合意で旧版互換の要求を取り下げたため、v1 の DTO・検証・署名を直接更新する（切り替えフラグなし）。追加値は署名に含め、町の区画・アイコンを判断材料にする Permission.townId は表示 hash にも含める。
- SEC-24 は実 HTTP／暗号／SQLite と隔離した relay・CLI fixture で、同名町の分離、全5テーマと未知/null、各 DTO の同一ID、削除・再起動・退場、他町の勇者の拒否、内部メタデータなし、許可 hash の町への束縛を検査する。証拠は [A3 検証記録](security/runs/2026-10-24-mobile-towns.md)。

### 勇者を動かす操作（A2）

A1 の前提「スマホからは札を作るだけで実行に進まない」は A2 で撤回した（A1 の検証記録は当時の事実として残す）。スマホから既存の勇者へ依頼を送り、新しい勇者を出陣させ、パーティーを組んで出発させられる。これは手元の Mac でのファイル変更・コマンド実行につながる**遠隔実行**であり、次の制限の上でだけ許す。

- **扱える操作**：作業の6操作（options・draft・prepare・form・embark・depart）だけ。active/review/done への状態変更、引き継ぎ、呼び戻し（mobile からの recall はない）、札の編集・採用・削除、ワークツリー、ターミナル入力、終了は扱わない。
- **Mac 側の端末ごとの作業許可（既定 off）**：Mac の「スマホ」画面で端末ごとに明示的に on にする。既定・旧版の登録・壊れた値は off。最初の選択は既存の Host／Origin／画面 token 検査を通る `/api/mobile/confirm` の任意 `allowWork:boolean`（省略false）で登録と同時に保存し、後からの切り替えは `/api/mobile/devices/:id/work` で行う。スマホからは変えられない。鍵・連番・登録は変わらない。`quest-options` の `allowWork` でアプリが状態を案内する。
- **窓口による効果の分類**（その時点の Mac の状態で判定し、アプリの申告は使わない）：
  - `spawn`：prepare の launch、embark。
  - `send`：勇者を指定した prepare の `mode:"send"`。さらに prepare／form のうち、しき（command）役を与える・忙しい勇者・送信待ちの本文や装備の変更が残る勇者・**別のクエストに入っている勇者を付け替える**ものは、勇者を動かし得るので送信と同じ扱い。
  - `depart`：depart。
  - `none`：札だけの prepare、空の form、待機中で未割当の勇者を command 以外の役で置く form／割当。
  - `none` 以外はすべて作業許可が必要。off でも options／draft の読み取りと `none` の操作はできる。既存の勇者の割当は Mac と同じ操作として認める（一律には禁止しない）。
- **操作ごとの本人確認（アプリ側）**：アプリは控えめに、勇者を指定または launch つきの prepare（mode を問わない）、メンバーが1人以上の form、すべての embark・depart で、毎回 OS の生体認証または端末のロック解除を求めてから連番を予約して送る（`mobileWorkMovesAgents`）。取り消し・失敗では連番も HTTP も使わない。結果は wire に載せず Mac も信用しない。窓口の分類の方が状態に応じて厳しく判定する。
- **作戦の段階づけ**：form で選んだ作戦はメモリの下書きにだけ置き、実際の作戦は出発まで「命令に従え（obey）」のまま。補助への依頼（ask）も出発まで作戦へ登録しない。許可された depart の最初の1回だけ作戦を有効にし、再開では作り直さない。フォームを保存しただけで、忙しいメンバーの停止をきっかけにレビュー・委任・調査が動くことはない。
- **出陣できるもの**：Claude と Codex だけ。Claude は `--permission-mode default`、Codex は `--ask-for-approval untrusted --sandbox workspace-write` を、装備（`--model` 等）の引数の**後ろ**に Mac が付ける。スマホから引数・環境変数・cwd・bypass 系の指定を渡す欄はない。拠点・preset・装備は Mac が発行した不透明 ID で選び、表示はラベルだけ。
  - 強制したモードは「すべての道具で確認する」という意味ではない。利用者の通常の CLI 設定の道具ごとの許可ルール（Claude の allow rules、Codex の設定）はそのまま効く。
  - 同じ Mac で人が手動で呼び戻した勇者は、mobile 外の通常の Mac の flag で起動し直される。
- **Pi**：新規の出陣は Mac が拒否し、options にも出さない。Mac で起動済みの Pi には依頼・参加ができるが、許可確認のフックがないため `permissionGate:false` として返し、アプリは送信・参加の前に「許可確認なしで実行される」と警告する。Claude は true、Codex は true（Codex 自身の承認で、スマホの許可フックは通らない）。
- **重複と頻度**：変更系の要求 ID（A1 の create と prepare・form・embark・depart）は同じ `mobile/quest-requests.json` の名前空間で、10分有効・未来60秒まで。効果の前に fsync で予約する。上限は端末ごとに変更系すべてで5件/分、`none` 以外（送信・出陣・出発）の合計で2件/分、出陣は1件/分・3件/時（出陣の予約は1時間保持）・同時に生きている勇者2人まで、Mac 全体でターミナル16個まで（既存の上限）。超過は一般拒否。同時2人の数はメモリ上の数え方で、再起動後は数え直しになる。
- **監査**：0600 の `mobile/work-audit.jsonl` に `{deviceId,operation,questId,heroId,time}` だけを効果の前に記録し、32KiB で1世代ローテートする（合計2ファイル）。prepare・form（メンバーごとの heroId）・spawn・send・出発の試行を残し、本文・依頼・パスは残さない。記録は**試行**であり配送の保証ではない。Mac の「スマホ」画面と見出しの件数は、読み込み・開いた時・定期取得の時に直近50件を出す。
- **部分的な出発**：depart はメンバーごとの step を持ち、各送信の直前に journal（`mobile/work-departures.json`）を `unknown` にして fsync してから送る。状態は `pending|sent|held|deferred|unknown`。`pending` だけを、人が明示的に操作した新しい requestId で再開できる。自動再送はしない。`unknown`（送ったか不明）は二度と送らない。完了した出発は再送しない。研究・レビューの作戦の deferred の扱いは既存の作戦の規則を使う。依頼文は既存の core の題（`questTitle`、200文字まで）と全文の目的（8000文字まで）から作る。
- **何が残り、何が消えるか**：
  - prepare の本文は Mac の既存のクエスト作成と同じくクエストの目的（purpose、最大8000文字）として常に保存される。
  - form で編集した本文と補助への依頼はメモリだけに置く（`saveConversation` の方針）。送った本文は Mac での送信と同じくクエストの出来事に残る。
  - journal に残るのは step の状態と、出発時の編成の HMAC-SHA256 だけ。鍵はプロセスごとの32バイト乱数で保存しないので、辞書照合できる指紋にならない。
  - フォームと出発の記録は `work-departures.json` に合計それぞれ1000件まで（自動では間引かない。上限に達したら利用者がアプリのデータを手で整理する）。
- **再起動**：未完了の出発は再起動後に `uncertain` として止め、再開しない（fail closed）。HMAC の鍵が変わるので以前の出発に対する操作 ID も無効になる。失われたフォームは `draftLost:true` とし、未出発なら入力し直して保存し直せる。完了した出発は再送しない。
- **フォームを編集できる条件**：状態が open、または mobile で作ったフォームの記録があり request／report／command／handoff の出来事がまだ無いクエストに限って waiting も可。通常の許可待ち・質問待ちで waiting になった進行中のクエストを編集可能にはしない。
- **応答**：失敗は一般拒否だけで、部分的な結果を返すのは depart の成功応答だけ。DTO に実パス・branch・cwd・引数を入れない。勇者の表示名は町の表示・重複の解消・上書きを経た名前、装備はラベルだけ、状態は busy／canTalk／active／questId。

### 採用しなかった鍵の束縛（Keystore／Keychain）

インストール済みの `expo-secure-store@58.0.2` と `expo-local-authentication@58.0.2` の API を確認した。

- `expo-secure-store` の `requireAuthentication` は Android Keystore の **AES 鍵**に `setUserAuthenticationRequired` を付け、保存した文字列の暗号化／復号を認証に結び付けるだけ。Ed25519 の署名鍵を Keystore 内に置いて署名する API はない。復号した秘密は JS へ渡り、`@noble/curves` が署名する。つまり保存中は暗号化されるが、使う時は JS へ取り出せる。
- Android の認証は `BIOMETRIC_STRONG` だけを検査する（端末の PIN へのフォールバックなし）。status の定期取得にも同じ鍵を使うため、鍵の読み出しを認証に結び付けると全要求で認証が必要になる。
- Mac は鍵の attestation（ハードウェア証明）を受け取らず、「直前に本人確認した」ことを検証できない。改造・侵害されたアプリは本人確認を飛ばして署名できる。
- このため Keystore に結び付けた Ed25519 は採用せず、本人確認は `LocalAuthentication.authenticateAsync`（`disableDeviceFallback:false`、`biometricsSecurityLevel:'strong'`、`requireConfirmation:true`）によるアプリ内の確認にとどめる。新しい native module・development build は不要で、既存の Expo クライアントで動く。安全性の主な支えは Mac 側の既定 off の許可・件数制限・強制した承認モード・取り消しである。実機でのこの確認の安全性は検証していない。

### 勇者の名前・報告の題・色（A6）

- 利用者の名前が最優先。未命名では TownNames の base が町の表示名／町のフォルダ名（keyの `.git` の親、非Gitはkey自体、旧keyなしのみpath）に完全一致する時だけ `種類 番号`（例 `Claude Code 1`、`pi 2`、不明なら `勇者 3`）。番号はPCと同じ履歴から取り、退場後も再採番しない。別worktreeの名前は維持する。勇者タブと発行・パーティー一覧は同じ部屋の勇者名を共有する。
- 報告は event.report から `mobileReportTitle` で漢字の題にする。PCのreportTitle・保存済みの題・successの判定は変えない。対応表はMOBILE-PROTOCOLのA6節。通知は元から固定文言だけなので変更なし。
- Hero / WorkHero だけに `variant:0|1|2|3|4`。PCのheroVariantをcoreへ共通化し、部屋の内部勇者ID（PTYだけなら結びついた勇者ID、無ければsession ID）から計算する。窓口発行IDからは計算しない。5値だけの多対一の色なので内部IDを復元・一意に推測できず、識別子には使わない。
- variantを応答署名の固定配列に含め、変更でその入力のhashも変わる。Permissionは変更せずA4 contentHashは不変。v1のまま両側のプロトコル・共有vectorsを同期更新。SEC-20/22/24を拡張し実HTTPで名前・題・署名改ざん拒否を確かめる。[検証記録](security/runs/2026-10-25-mobile-names-variant.md)。画面実装は別作業。

### 装備のモデル／effort の表示（A5）

- quest-options の武器は `{id,name,model:string|null}`、はちまきは `{id,name,effort:MobileEffort|null}`。共通Choiceや拠点は変更しない。WorkHeroにも model/effort を平坦な必須欄として加え、既存の武器／はちまきの名前を残す。
- 値は読み込み済みの本体装備マスタ（equipment.json、既存の利用者上書きを含む）の model/value からそのまま取る。名前から推測しない。勇者の値は既知の選択済み装備であり、CLIの現在値／既定値を観測した値ではない。
- model は英数字から始まる1〜64 ASCII文字（英大小文字・数字・`.` `_` `:` `/` `-`）。URL、ドライブパス、`.`/`..` のパス成分も拒否する。effort は off/minimal/low/medium/high/xhigh/max の7値（最大7文字）だけ。詳細はMOBILE-PROTOCOLのA5節。
- 不明・不適合なら **その欄だけnull**。選択肢と名前を消さず、既存の装備選択を妨げない。モデル名はグローバルな固定一覧で制限せず、利用者登録済みの短いprovider/modelも扱う。任意の入力値を起動へ使う欄は増やさず、起動要求は従来どおり発行済み不透明IDだけ。
- 追加値とnullはすべて応答署名の対象。Permissionは変えないためA4のcontentHashは不変。v1をその場で同時更新し、共有vectors・両側の純粋検査とSEC-22の実HTTP検査を拡張する（新SEC番号なし）。[検証記録](security/runs/2026-10-25-mobile-equipment.md)。画面担当向けの表示・null・ID送信の注意はアプリ側MOBILE-PROTOCOLに記載。

### 許可の理由と変更本文（A4）

- `work: {questId,title} | null` は認証済み端末の現担当クエストを許可受信時に固定したもの。台帳 `QuestLedger.current` の確定した ID／題を使い、端末・町・勇者を照合する。request 本文は保存設定や複数メンバーの依頼と混同しないため追加しない。不明・未割当・終了済みは null。パス・cwd・branch から作業を推測しない。
- `change` は Write の `{kind:'write',text,omitted}`、Edit/MultiEdit の `{kind:'edit',edits:[{before,after,replaceAll}],omitted,omittedEdits}`、取得不能の `{kind:'unavailable'}`。Bash は従来の content にコマンド、他の道具も従来どおり change=null。これは置換の要求であり、実ファイルの diff ではない。
- 本文は UTF-16 で合計2000文字、content と合わせて3000文字まで。置換は16組、応答は16件。制御文字の JSON escape 込みでも暗号文512KiB／HTTP 1MiB 内。サロゲート対を分断せず、制御文字は生値を保持し画面の visible で可視化する。
- 追加した全値を contentHash に含める。スマホの承認は従来の外側 omitted=0 に加え、本文 omitted=0・omittedEdits=0・unavailable でない場合だけ。本文が切れたままの承認は拒否し、拒否は可能。work=null だけなら承認不可にはしない。
- Mac の許可カード／WS とその既存の判断は変えない。追加本文は待機中メモリだけ（最大120秒）で、台帳・監査・push に保存／配信しない。既存の v1 を同時更新し互換フラグは作らない。UI 担当はアプリの `docs/MOBILE-PROTOCOL.md` の A4 節に従い、全受信本文と省略／取得不能を表示する。
- SEC-25：実 HTTP／暗号／SQLite／隔離 relay・CLI で、他勇者・他町との非混同、本文・作業を変えた hash の拒否、省略／欠落時の承認拒否と拒否可、最悪16件応答を検査する。[実行記録](security/runs/2026-10-25-mobile-permission-content.md)。

### 許可の判断

- アプリは承認・拒否の前に、必ず生体認証（または端末のロック解除）を求める。
- `decide` には、許可要求の ID と、画面に表示した内容のハッシュを含める。Mac はハッシュが今の内容と一致し、期限内で、まだ答えていない時だけ受け付ける。
- 判断は既存の `permission-decision` と同じ処理へ渡す。自動承認はしない。ブラウザと同時に答えた場合は、先に届いた方を採る。
- 誰がいつ判断したか（端末 ID・許可 ID・結果・時刻）を窓口の記録に残す。コマンドの本文は残さない。

### 通知

- 送る契機は、許可待ち・報告・失敗。題は「Yushario」、本文はpermission「確認が必要です」、report「報告が届きました」、error「勇者が止まりました」の種類ごとの固定文言。既存data.kindと同じ分類だけで、作業の中身・町名・勇者名・コマンド・パスは載せない。時間制約のある利用者向け通知として Expo の priority は常に high。Android の専用チャンネル ID は `alerts` とし、窓口は `channelId: "alerts"` を送る。アプリ側で HIGH の重要度で作成する（配送優先度とは別）。
- 自動通知は端末ごと・種類ごとに、Expoのticketがokになってからその端末が認証済みの窓口要求を送るまで同じ種類を抑止する。送信中も同じ連番の端末・種類の重複は送らない。ネットワーク失敗・ticketエラー・tokenなしでは印を付けず、次の通知を妨げない（自動再送はしない）。
- 抑止印は既存 `mobile/state.json` の各端末の `notifiedKinds`（重複なし最大3種類）で保存し、再起動でも保持する。旧記録の欄なしは空として読み、鍵・連番・allowWorkは維持。認証・時刻・連番を検査して連番を耐クラッシュ保存する時に全種類の印を解除する。無認証／署名不正／replayでは解除せず、接続後に到着した古いticketで再抑止しない。新しい保存ファイルは作らず、push診断ログの6項目も不変。
- permission通知だけに `ttl` を付け、送信開始時の許可期限までの残り秒を切り捨てる（最大120秒、1秒未満／期限切れは送らない）。期限は受信した許可要求のexpiresAtで、report/errorにはttlを足さない。通知が届いても許可の期限を延長せず、窓口で改めて確かめる。
- アプリは通知を開いた後、窓口へ `permissions` や `reports` を取りに行く。経路に届かない時は「Mac に接続できません」と表示する。
- 通知用 ID は窓口のファイルに保存し、端末の登録を消した時に消す。この ID が漏れても、できるのは偽の「確認が必要です」を送ることだけで、承認はできない。
- Expo の ticket の `ok` は受付だけで、配送の保証ではない。5秒後に receipt を照会し、未確認ならさらに30秒・120秒後に照会する（最大3回）。確認できなくても同じ通知を自動再送しない。ticket／receipt の DeviceNotRegistered は、送信時と同じ通知 ID がまだ登録されている場合だけ消す。
- Mac の「スマホ」に端末ごとの最後の通知を「配送済み／失敗（安全な error code）／未確認／通知 ID なし」で出し、「テスト通知を送る」でその端末だけへ同じ固定文言を送れる。配送済みは FCM/APNs が受理したことまでで、端末の表示・音・閲覧を保証しない。テストの kind は permission（ttlは120秒以下）で、許可要求や承認は作らない。人がMacで押したテスト通知は抑止を迂回して毎回送り、自動通知の印も付けない。
- 通知の記録はメモリの直近50件と、`mobile/push-delivery.jsonl`（0600、32KiBで1世代だけローテート、合計64KiB以下）。送信開始時刻・端末 ID・kind・ticket/receipt の状態・許可した error code だけで、通知 ID・ticket ID・題／本文・provider の生の message・作業内容は残さない。途中で終了した通知は未確認にし、再起動で成功したことにしない。

- A7のSEC-02/21・07/08拡張は実HTTPの承認API・窓口・ローカル偽Expoで検査し、Expo/APNs/FCMへは送らない。[検証記録](security/runs/2026-10-25-mobile-onboarding.md)。スマホv1の要求・応答と暗号vectorsは変更なし。

### 端末の取り消し

- Mac の画面に登録済みの端末を一覧し、個別に取り消せる。取り消した端末の要求はすぐに断る。
- アプリからは自分の登録だけを消せる。

## 検証と証跡

- 証跡は `docs/security/`（窓口）とアプリのリポジトリの同じ場所に置く。
  - `threat-model.md`：上の表を正として育てる。
  - `checklist.md`：アプリは OWASP MASVS、窓口は OWASP ASVS レベル2の該当項目ごとに、対応と証拠へのリンクを書く。
  - `runs/<日付>-<コミット>.md`：検証した日付・対象のコミット・手順・結果・使った道具の版。
- 自動の検査（CI で毎回実行）
  - SEC-xx のうち自動化できるもの。窓口の検査は、実際の HTTP で窓口を立てて要求を送る形にする。
  - 共有のテスト用データによる暗号の検査（Mac 側とアプリ側の両方）。
  - CodeQL、依存の脆弱性検査（`npm audit` と OSV-Scanner）、秘密情報の検査（gitleaks）。
- 手動の検査（リリースごと）
  - 実機での操作の確認（生体認証・取り消し・紛失を想定した手順）。
  - アプリのビルドを MobSF で検査する。
- リリースの条件：そのコミットの `runs/` がそろい、未対応の SEC 項目がないこと。

## 進める順番

1. この文書の合意と、`ARCHITECTURE.md`・`AGENTS.md` の更新（下の「本体側で変えること」）。
2. 暗号とプロトコルの仕様書・テスト用データ（Yushario の `src/core` に純粋関数として置く）。
3. モバイル窓口（Yushario 本体、ブランチ + PR）と SEC 検査。
4. アプリのリポジトリを作り、Android でペアリング・状態・許可・報告・通知を作る。
5. iOS シミュレーターで確認する（APNs の実配送は Apple Developer の登録後）。
6. 検証の実施と証跡のまとめ。
7. Apple Developer に登録し、TestFlight で友人に配る。

## 本体側で変えること

- `ARCHITECTURE.md` の「PoC でやらないこと」から、スマホ対応とインターネット経由の利用（窓口の範囲に限る）を外し、窓口の境界と許可リストを「インタフェース」に書く。
- `AGENTS.md` のテストの規則に、窓口のセキュリティ検査を例外として加える（実際の HTTP で窓口を立てる形）。
- 暗号・窓口・通知に追加依存はなし（Node 標準の `crypto`／`http`／`fetch`）。登録画面の QR 符号化だけは、独自実装を避けるため `qrcode-generator`（実行時の依存なし、MIT）を使う。
