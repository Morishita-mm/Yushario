# YusharioのADE再評価：可視化から、仕事を残して確かめる場へ

評価日：2026-10-15。対象：`2bc8718`。前回：[ADE-RESEARCH.md](ADE-RESEARCH.md)（2026-10-14）。**レビューと提案であり、実装仕様の変更ではない。**

## 1. 結論

**前回から評価を明確に上げられる。可視化中心のアプリから、小規模な日常開発で試せるADEの土台になった。**

前回の最優先課題だった「永続的な仕事」「worktree」「実際の差分」「検証の証拠」が実装され、パーティー・管理CLI・引き継ぎ・プレビューも加わった。これは絵の上の機能追加ではなく、仕事のライフサイクルを支える変更である。「仕事台帳がない」「Codexは端末のみ」「コミット済み変更を見られない」という前回の指摘は、今には当てはまらない。

ただし、次の二つを分けたい。

- **ADEとして成立するか：成立する方向に大きく進んだ。** RPG表現と実務の対象の対応も良い。
- **安心して成果を採用できるか：まだ詰めが必要。** 誤った合格印と古いフォームによる状態の上書きを再現した。また、鑑定→修正指示→採用対象の記録→PRという最後の区間は手作業が多い。

次の優先順位は、機能数ではなく **正しい合格 → 正しい状態 → 安全な引き継ぎ → 成果を届ける導線**。全自動協調・クラウド・追加演出を先に増やす段階ではない。

## 3. 前回の不足はどこまで埋まったか

| 観点 | 今回の到達点 | 再評価 |
| --- | --- | --- |
| 仕事の永続化 | SQLiteにクエスト・目的・状態・担当・出来事・検証を保存。仕事とセッションを分離 | **大きく解消**。セッション一覧から仕事台帳へ進んだ |
| リポジトリの同一性 | 共通Gitディレクトリの実パス。同名repoを区別し、worktreeは同じ町へ | **解消**。町＝repoの意味が安定した |
| 分離作業 | base/branch/pathを選んでworktree作成。同じ場所の作業を警告。変更・端末のある拠点は撤去しない | **基本を解消**。依存準備・port割当は手動 |
| 差分鑑定 | 未コミットとbranch全体の比較、行番号、外部エディタへの入口 | **閲覧は解消**。行コメント付きの差し戻しは未対応 |
| 検証と受入条件 | 条件ごとの証拠・拠点・指紋、未実行/成功/失敗/古い/不明、採用時の確認 | **設計は大幅改善**。ただし誤合格の残りを確認（指摘1） |
| 再起動後の継続 | 台帳と拠点が残り、端末なしでも鑑定できる。本文保存は選択制 | **大きく解消**。PTY・会話窓の復元と同一ではない |
| 協調・引き継ぎ | 役割、単独の書き換え役、役割外編集の通知、編集可能な巻物 | **基本を解消**。停止・配送・開始の確認は残る |
| 管理CLI | `yushario quest read/note/send/invite/review`。指揮役の範囲を限定し、仲間の追加は人が承認 | **実装済み**。全町を操作する汎用CLIではないが、最初はこの制約でよい |
| Codex | 勇者・会話・報告・resume・パーティー配送に対応 | **大きく改善**。検証証拠・MP等はClaude/piと同等ではない |
| 動く成果の確認 | ローカルURLを仕事に関連付け、別タブ・任意スクリプトからエラーを依頼へ戻す | **基本を解消**。ブラウザ自動操作・実行環境管理ではない |
| PR/CI・取り込み | アプリ内のcommit/push/PR/merge、CI連携は対象外 | **依然不足**。外部CLIで可能だが、仕事との結び付きが薄い |
| 高速な横断操作 | 地図以外に伝令・勇者・クエスト一覧、判断待ち優先、キーボード改善 | **改善**。横断検索・次の判断への最短移動は伸ばせる |
| 添付・参照・使用量 | ファイルを開く入口はあるが、選択範囲/画像の依頼添付、quota/cost等はない | **残る**。誤採用対策より優先しない |

## 4. 確認した問題と残る実務上の穴

優先度はこのレビューでの判断。**P1＝成果や状態を誤認させるため先に直す、P2＝日常利用の次の改善。** 実装不具合と、意図的に未実装の製品上の不足を区別する。

### 1. P1・再現済み：成功したコマンドと、検証されたコードが一致しない

**場所：** `src/core/checks.ts:30–77`、`src/server/checks.ts:82–99`。

`&&` だけなら確実なコマンドとして扱い、完了通知後に端末の起動フォルダの指紋を取る。このため、次の二つで誤った合格印を再現できる。

| 再現 | 実際に確かめたこと | アプリの判定 |
| --- | --- | --- |
| `cd /別フォルダ && npm test` | 別フォルダのテストは終了0。クエストの拠点の `npm test` は終了1 | クエストの `npm test` が **ごうかく** |
| `npm test && cp changed.txt value.txt` | テスト成功後に対象コードを変更。変更後の `npm test` は終了1 | 変更後の指紋が付き **ごうかく** |

後者のテストは `value.txt` の内容を検査する小さなfixtureで確認した。リダイレクトを使う変更は不明になったが、単純な `cp` では通った。したがって「危険な記号を除けば安全」という問題ではない。

**影響：** 合格していない条件に印が付き、採用時の未合格確認も出ない可能性がある。これはRPGの印を信用するほど危険になる。

**提案：** 万能なシェル解析は作らず、証明できる範囲を絞る。実行場所を確かめられない `cd` 等、任意の前後処理を含む並びは、まず不明にする。取得できるCLIではツールのcwdと実行前後の作業状態を結び付け、検証後の変更・並行編集を合格にしない。コマンドの終了0と、現在コードの検証済みを分離する。単独コマンドでも別ツールの同時編集には注意が必要。

### 2. P1・再現済み：題を保存しただけで、新しい仕事の状態を古い状態へ戻せる

**場所：** `src/web/rpg/quests.ts:41–46, 96–100`、`src/web/town/quest-card.ts:13–30`。

再現手順：

1. `active` のクエスト札を開き、題だけを編集する。
2. その間にサーバー側で `review` へ進める（再現では別のAPI要求。実際には報告でも起こり得る）。
3. 札は書きかけ保護のため全体の再描画を止め、状態欄は `active` のまま。新しい情報がある表示もない。
4. 「ほぞん」で題・目的・状態をまとめて送るため、DBの状態が **`review` → `active`** に戻ることを確認した。

**影響：** 作業が進んだ事実が意図せず上書きされる。入力中は検証印・パーティー等の読み取り情報も古くなり、指揮所としての信頼性が落ちる。

**提案：** 下書きは守りつつ、読み取り部分の更新は止めない。保存は変更したフィールドだけにし、状態を明示変更する場合は最新状態との違いを確認する。最小対応でも「新しい報告あり／更新あり」と再読込の入口を出す。札全体を作り直すための汎用UI基盤は不要。

### 3. P2・再現済み＋設計上の制約：引き継ぎ受付が、引き継ぎ完了に見える

**場所：** `src/server/party-api.ts:58–78`、`src/server/pty-actions.ts`、`src/web/town/quest-handoff.ts:51–55`。

- 受け手が作業中の場合、APIは `delivered: false`（預かり）を返す。
- それでも巻物の画面は「巻物を わたした！」。配送結果を表示に使っていないことをUIでも確認した。
- 書き換える役を移すと、**旧担当も受け手も作業中のまま**、台帳上の書き手だけが変わることを確認した。旧担当の停止も、受け手による巻物の実行も保証しない。

役割が助言であり、CLI内の権限を強制しないのは明示された設計で、OSの書き込み隔離がないこと自体を不具合とはしない。ただし、人の思い込みを防ぐ導線は必要。

**提案：** 「巻物をあずかった」「入力を届けた」「受け手が作業を始めた」を分ける。書き換え役の移転前には旧担当が作業中と警告し、人が中断要求→停止確認を選べるようにする。不明なら完了と言わず、同じ依頼を自動再送しない。同じ拠点で続けるか、別拠点へ成果を移すかも明示する。自動停止・自動mergeは不要。

### 4. P2・製品上の不足：鑑定から成果の受領まで、対象と判断が十分に残らない

**場所：** `src/web/rpg/review-window.ts`、`src/server/review.ts:135`、`src/server/quest-ledger.ts:86–93, 119–122`。

差分閲覧はもうある。しかし、次は別の仕事である。

- 気になったファイル・行・比較元を、そのまま修正依頼にする。
- どのHEAD／作業状態を確認し、なぜ採用・差し戻ししたか残す。
- 対象のPRとCI、取り込み先、次に行うGit操作を確認する。

現在の「かんてい ずみ」は鑑定APIを読んだ段階で記録される。全ファイルを読み終えた、承認した、という証拠ではない。また `done` への状態変更は残るが、その操作で採用対象の指紋や理由を固定していない。報告時のHEAD記録があることとは分けたい。

**提案：** 最初は選択した差分の場所を会話の下書きへ渡し、「確認済み／要修正」の判断を対象とともに記録する。採用時には対象HEAD・指紋・検証・任意の理由・PR URLを残す。PRを開く／作成結果を結び付ける入口から始め、Gitの破壊的操作まで内製しない。`done` はGit取り込み完了ではないと明記する。

### 5. P2・操作性：仕事を見る画面が、設定・編集する画面に寄っている

クエスト札は題・目的の編集から始まり、検証の追加フォーム、URLの追加フォーム、パーティー、巻物、出来事が縦に続く。800px幅でも到達はできたが、少人数・少履歴のfixtureでも長いスクロールになる。

**提案：** 既定は「目的／今の担当と拠点／必要な判断／検証／鑑定・再指示」を短く見せる。題や条件の編集、URL追加、古い出来事は折り畳む。主操作を「鑑定する・なおしてもらう・採る」に寄せ、詳しい設定を消す必要はない。横断検索や次の判断への移動も、仕事数が増えてから効く改善である。

## 5. 競合との距離と、今回強くなった点

| 比較対象 | 今回縮まった距離 | まだ学ぶところ |
| --- | --- | --- |
| Orca | repo/worktree/quest/sessionの区別、実diff、永続台帳、役割付きの管理CLI | 差分コメント・issue/PR連携、判断・試行・取り込みを一続きにすること |
| Superset | worktreeと引き継ぎ、複数CLI、成果の閲覧 | コンテキスト付き再指示、準備済みworkspace、再開・引き継ぎの操作摩擦 |
| Conductor | 仕事ごとのbranch、checks、コミット済み成果の鑑定 | PR/mergeまでの一周、checkpoint、受入対象を明確にすること |
| cmux | 既存CLIを残しつつ、URL・通知・管理コマンドを足した | 大量の仕事から次の判断へ移る速さ。paneを増やすだけの競争はしない |
| Gas Town | 台帳、役割、指揮役、引き継ぎという要素が揃った | 受付・開始・完了・受入の区別。自動DAGやmerge queueまで真似る必要はない |
| Pixel Agents | RPG表示に加え、仕事・拠点・検証・鑑定・配送を持つ | 見た目だけでなく実務の一周が差別化になる。競合の将来機能を実装済みとは扱わない |

### 特に良い変更

1. **RPGの名詞が、本物の対象になった。** クエストは永続仕事、拠点はworktree、巻物は編集して渡せる引き継ぎ。名前だけのパーティーではなく、役割と履歴がある。
2. **アプリ内ハーネスを作らずに指揮できる。** 既存CLIへ保存・配送・表示を提供し、指揮内容は人かCLIが決める。薄い管理CLIも実現できている。
3. **不明を捏造しない方針を守っている。** Codexの公式出力に終了コードがないため、検証合格・編集成功・MPを推測しないのは正しい。READMEの制約明示も良い。ただし画面上の印もCLIごとの差を説明したい。
4. **永続化とプライバシーを両立する方向が良い。** 本文保存を選択制にし、metadata・判断履歴を残す。既定オフでは巻物や返事の本文が再起動後に戻らないため、「残る物／残らない物」は保存設定の近くにも出したい。
5. **安全なGit閲覧・撤去の配慮がある。** 外部diff等の無効化、範囲と出力の制限、dirtyな拠点の撤去拒否は、見栄えより重要なADEの基礎である。worktreeは権限sandboxではない。

## 6. RPGを薄めずに、次の改善を取り込む

| RPGの表現 | 次に結び付ける実務 | 表示上の約束 |
| --- | --- | --- |
| 試練の合格印 | 実行場所・対象コード・検証結果の一致 | 別拠点／検証後変更／不明では光らない |
| 冒険の書 | 新しい報告と、人の編集中の下書きの両立 | 書きかけを守っても、世界の現在状態を隠さない |
| 引き継ぎの巻物 | 預かり→入力配送→開始、旧担当の停止状況 | 巻物の受付と担当交代の完了を混ぜない |
| 宝箱の鑑定 | 比較対象付きの確認・指摘・修正依頼 | 窓を開いただけなら「鑑定をひらいた」。承認印は別 |
| 町へ成果を届ける | 採用対象・PR・CI・取り込み先 | 「採った」と「mainへ取り込んだ」は別の事実 |
| 伝令・作戦卓 | 次に判断が必要な仕事への直接移動 | 地図の移動や演出を実務の待ち時間にしない |

HP・MP・Lvを品質・完了率・料金へ読み替える必要はない。地図は状況の俯瞰、札と差分は根拠の確認という二層構造を守る。RPGを削るのではなく、**RPGが指す事実の精度を上げる**ことが次の差別化になる。

## 7. 次に進める順序と終了条件

### 先に：信頼性の仕上げ

- 誤合格の二つの再現を不明／古いにする。単独の正常な検証は引き続き合格できること。
- 題だけの保存で、新しいレビュー待ちを巻き戻さない。下書きを保ち、新しい判断材料を通知すること。
- 引き継ぎで預かり・配送・開始を区別し、旧担当の作業中を見落とさないこと。

### 次に：一件を出荷する最後の区間

- 差分の場所付き修正依頼、採用対象と判断の保存、PRへの入口をつなぐ。
- 一枚目を作戦卓にし、編集・設定・古い履歴は必要時に開く。
- Codexで自動証拠が取れない条件は理由を示す。人の確認を足すなら、自動検証の合格とは別の印にする。公式連携の制約を迂回しない。

### その後：実際の仕事で比較する

1. 3件のうち判断待ちを見つけて答える。
2. 同じrepoの2件を分離し、実装→レビュー→修正→再検証→PRへ進める。
3. テスト後の変更や別フォルダの成功を、誤って採用しない。
4. 旧担当が作業中のまま渡そうとし、重複編集を避ける。
5. サーバー再起動後、何を採用し、何が未完か辿って続ける。

見るのは発見時間、画面往復、編集衝突、誤採用、再開の成功。競合との優劣や「16人でも分かりやすい」は、同じ課題で測ってから述べる。

**総評：足りなかった基礎機能はかなり埋まった。次は「さらに多機能にする」より、「任せた仕事を安心して受け取れる」ことを仕上げたい。**
